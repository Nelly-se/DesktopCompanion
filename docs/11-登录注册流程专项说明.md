# 11 - 登录注册流程专项说明

本文专门说明 SpiritDesk 的登录、注册与登出流程，适合写实验报告、答辩讲解或快速理解认证相关代码。

## 1. 总体设计

SpiritDesk 的账号系统是一个可配置的 Cookie 登录门禁。开关由 `appsettings.json` 中的 `SpiritDesk:Auth:Enabled` 控制：

- 关闭时：访问页面不需要登录，适合本地桌面 Shell 免登录运行。
- 开启时：除 `/Login`、`/Register`、`/Logout`、`/Error`、`/Privacy` 外，大部分 Razor Pages 都需要先登录。

登录成功后，系统通过 `SpiritDesk.Auth` Cookie 保存当前用户身份。后续请求会自动携带 Cookie，ASP.NET Core 再根据 Cookie 判断用户是否已登录。

## 2. 相关文件

| 文件 | 作用 |
|------|------|

| `src/SpiritDesk.Web/Auth/WebAccountAuth.cs` | 统一用户名校验和规范化 |
| `src/SpiritDesk.Web/Pages/Login.cshtml` | 登录页面表单 |
| `src/SpiritDesk.Web/Pages/Login.cshtml.cs` | 登录逻辑：校验账号密码、签发 Cookie |
| `src/SpiritDesk.Web/Pages/Register.cshtml` | 注册页面表单 |
| `src/SpiritDesk.Web/Pages/Register.cshtml.cs` | 注册逻辑：校验输入、写入账号和用户档案 |

## 3. 配置开启流程

项目启动时，`Program.cs` 调用 `SpiritDeskWebHost.Build(args)` 创建 Web 应用。`SpiritDeskWebHost` 会读取配置：

```json
"SpiritDesk": {
  "Auth": {
    "Enabled": true,
    "Username": "",
    "Password": "",
    "AllowRegistration": true
  }
}
```

各字段含义如下：

| 配置项 | 含义 |
|--------|------|
| `Enabled` | 是否启用登录门禁 |
| `Username` | 可选的系统引导账号用户名 |
| `Password` | 可选的系统引导账号密码 |
| `AllowRegistration` | 是否允许用户打开注册页并创建账号 |

当 `Enabled=true` 时，`SpiritDeskWebHost` 会注册 Cookie 认证，并设置：

- 登录页：`/Login`
- 登出页：`/Logout`
- Cookie 名称：`SpiritDesk.Auth`
- Cookie 有效期：12 小时
- Cookie 使用 `HttpOnly`，前端 JavaScript 不能直接读取

## 4. 注册流程

注册入口是 `/Register`，页面由 `Register.cshtml` 显示，后端逻辑在 `Register.cshtml.cs`。

### 4.1 访问注册页

用户访问 `/Register` 时，系统先判断：

1. 如果没有开启认证，直接跳回首页。
2. 如果不允许注册，跳转到 `/Login`。
3. 如果用户已经登录，跳回首页。
4. 以上都通过后，显示注册表单。

### 4.2 提交注册表单

用户提交用户名、密码、确认密码后，`OnPostAsync` 会依次校验：

1. 用户名格式是否合法：长度 3 到 32，只允许字母、数字、下划线和短横线。
2. 密码长度是否至少 6 位。
3. 密码是否超过 128 位。
4. 两次输入的密码是否一致。
5. 用户名是否和配置中的引导账号冲突。
6. 数据库 `WebAccounts` 表中是否已经存在同名账号。

用户名会通过 `WebAccountAuth.NormalizeUsername` 统一处理：去掉首尾空格，并转成小写。这样可以避免 `Alice`、`alice`、` ALICE ` 被当成三个不同账号。

### 4.3 写入数据库

校验通过后，系统会创建两个对象：

1. `WebAccount`：负责登录认证，保存规范化用户名、密码哈希和创建时间。
2. `UserProfile`：负责业务档案，保存昵称、当前精灵、心情、亲密度、等级、金币等数据。

密码不会明文入库，而是通过 `IPasswordHasher<WebAccount>` 生成 `PasswordHash`。注册成功后，系统不会直接自动登录，而是通过 `TempData["LoginNotice"]` 在登录页显示“账号已创建，请登录”的提示，然后跳转到 `/Login`。

## 5. 登录流程

登录入口是 `/Login`，页面由 `Login.cshtml` 显示，后端逻辑在 `Login.cshtml.cs`。

### 5.1 访问登录页

用户访问 `/Login` 时，系统先判断：

1. 如果没有开启认证，直接跳回首页。
2. 如果用户已经登录，跳转到原本想访问的页面，或者跳回首页。
3. 否则显示登录表单。

登录页面中还会根据 `AllowRegistration` 决定是否显示“没有账号？注册”的链接。

### 5.2 提交登录表单

用户提交用户名和密码后，系统会先检查是否为空，再把用户名规范化。

接着有两种账号来源：

1. 配置中的引导账号：如果 `SpiritDesk:Auth:Username` 和 `SpiritDesk:Auth:Password` 配置了值，且用户输入匹配，就直接登录。
2. 数据库账号：如果不是引导账号，系统会到 `WebAccounts` 表按规范化用户名查找账号，再用 `PasswordHasher.VerifyHashedPassword` 校验密码。

如果账号不存在或密码错误，页面统一提示“用户名或密码不正确”。代码中还加入了短暂随机延迟，避免错误响应过快被用于简单撞库。

### 5.3 签发 Cookie

登录成功后，`SignInAsync` 会创建一个包含用户名的 `Claim`，再调用：

```csharp
HttpContext.SignInAsync(
    CookieAuthenticationDefaults.AuthenticationScheme,
    new ClaimsPrincipal(identity));
```

ASP.NET Core 会把身份信息写入加密后的 `SpiritDesk.Auth` Cookie。之后用户访问其他页面时，只要 Cookie 有效，就会被识别为已登录。

## 6. 登出流程

登出入口是 `/Logout`。页面通常通过 POST 表单触发登出。

`Logout.cshtml.cs` 中会调用：

```csharp
HttpContext.SignOutAsync(CookieAuthenticationDefaults.AuthenticationScheme);
```

这一步会清除当前浏览器里的登录 Cookie。清除后，用户会被重定向到 `/Login`。

## 7. 账号与用户档案的关系

本项目把“登录账号”和“业务档案”分开设计：

- `WebAccount` 管认证：用户名、密码哈希、创建时间。
- `UserProfile` 管业务数据：昵称、精灵、心情、等级、金币等。

两者通过 `AccountUsername` 关联。注册时，`WebAccount.Username` 和 `UserProfile.AccountUsername` 使用同一个规范化用户名。这样用户登录后，系统就能根据当前 Cookie 中的用户名找到对应的个人档案，显示自己的精灵、任务和聊天历史。

## 8. 一句话流程总结

注册时，系统校验用户名和密码，把密码哈希写入 `WebAccounts`，同时创建一份 `UserProfile`；登录时，系统先匹配配置引导账号，再查询数据库账号并校验密码，成功后签发 `SpiritDesk.Auth` Cookie；登出时清除 Cookie，用户重新回到登录页。

## 9. 答辩可用说法

本项目使用 ASP.NET Core Cookie Authentication 实现登录状态管理，账号数据由 EF Core 保存到 SQLite。注册时只保存密码哈希，不保存明文密码；登录成功后由服务端签发 `HttpOnly` Cookie，后续页面访问通过 ASP.NET Core 中间件自动完成身份识别和页面授权控制。
