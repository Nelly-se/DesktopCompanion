# 05 - 常见方案对比与答辩话术

## 1. 桌面 + 界面：几种常见路线

| 方案 | 界面技术 | 代表 | SpiritDesk |
|------|----------|------|------------|
| **原生 UI** | WPF / WinUI 画控件 | 传统桌面软件 | 仅顶栏 + 浮球 |
| **嵌入式浏览器** | WebView2 / CEf | 很多现代桌面应用 | **主界面** |
| **Electron** | Chromium + Node.js | VS Code、Slack | ❌ 未用 |
| **纯 Web** | 只浏览器访问 | 管理后台 | `run-web.ps1` 可选 |

SpiritDesk 选的是：**WPF 壳 + WebView2 显示 Web 项目**，业务集中在 ASP.NET Core。

---

## 2. 为什么不用 Electron（老师可能问）

| 对比 | Electron | WPF + WebView2 |
|------|----------|----------------|
| 运行时 | 捆绑 Chromium + Node，体积大 | 用系统 WebView2 Runtime，exe 相对小 |
| 技术栈 | 前后端 often JavaScript | 本项目 C# 统一（Web + Shell） |
| 适合 | 跨平台桌面 + 大量前端生态 | **Windows 桌面 + 已有 ASP.NET 站点** |

答辩说法：

> 我们目标是 Windows 桌面陪伴程序，已有 ASP.NET Core Web 项目，用 WebView2 嵌入站点比再套一层 Electron 更轻，也和课程 C# 技术栈一致。

---

## 3. 为什么主界面不全部用 WPF 画

| 全 WPF | WebView2 嵌 Web |
|--------|-----------------|
| 每个页面都要 XAML + C# | 页面用 Razor + CSS，改 UI 快 |
| 和浏览器演示不是同一套 | **浏览器 / 桌面同一套页面** |
| 登录、任务、聊天都要重写 | 直接复用 `SpiritDesk.Web` |

浮球仍用 WPF，因为需要**系统级透明置顶窗口**，不适合塞进网页里。

---

## 4. 前端知识在答辩里怎么说

不必声称「纯前端框架 Vue/React」，应说：

> 界面层是 **Razor Pages 服务端渲染（SSR）** 的 HTML，样式和脚本在 **wwwroot**；桌面端用 **WebView2** 加载这套页面。前端主要负责页面结构、CSS 和少量 JS；业务与数据在 C# 的 PageModel 和 Service 里。

| 技术 | 在本项目角色 |
|------|--------------|
| HTML | cshtml 输出 |
| CSS | `wwwroot/css/site.css`、主题色 |
| JavaScript | `wwwroot/js/site.js`，辅助交互 |
| WebView2 | 显示上述页面，不是写 UI 的框架 |

---

## 5. 常见问题标准答法

**Q：WebView2 是什么？**  
微软嵌入式浏览器控件，Chromium 内核，用在 WPF 窗口里显示网页。

**Q：桌面程序和网站是什么关系？**  
Shell 是宿主，内嵌 WebView2 访问 SpiritDesk.Web；网站可单独浏览器打开，是同一套后端。

**Q：端口谁定的？**  
WebView2 不定端口；Shell 本地模式随机端口启动 Web 子进程；只跑 Web 时固定 5160。

**Q：浮球为什么不用 WebView2？**  
浮球要系统置顶、透明、拖拽，用 WPF 原生窗口；数据用 HTTP API 从 Web 服务拉。

**Q：登录状态存在哪？**  
账号在 SQLite；当前会话在 WebView2 的 Cookie 里，由 ASP.NET Core Cookie 认证管理。

## 6. 推荐演示顺序（答辩）

1. `run-shell-with-auth.ps1` → 展示 WebView2 内登录页  
2. 登录后首页、任务、聊天（说明是网页）  
3. 指出顶栏是 WPF、中间是 WebView2  
4. 展示桌面浮球（说明是 WPF + API，不是网页）  
5. 可选：`run-web.ps1` 说明同一套 Web 也能浏览器访问
