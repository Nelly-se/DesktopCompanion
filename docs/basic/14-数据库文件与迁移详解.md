# 14 - 数据库文件、Git 与迁移（和 TypeORM 对照）

> 读完 [13-EF是什么详解.md](./13-EF是什么详解.md) 后，常会追问：  
> **「`spiritdesk.db` 不在 Git 里，每个人本地库不一样，是不是不对？要不要像 TypeORM 那样每人一份带时间戳的 migration？」**  
> 本篇把 **表结构（Schema）** 和 **运行数据（Data）** 分开讲，并对照本项目现在的做法。

实现代码见：`SpiritDeskDbContext.cs`、`DatabaseBootstrapper.cs`、`SpiritDeskService.EnsureInitializedAsync`。

---

## 0. 先给结论（答辩可背）

| 问题 | 答案 |
|------|------|
| `spiritdesk.db` 要不要进 Git？ | **不要**。它是本机运行产生的 **数据文件**，不是源代码。 |
| 每个人本地的库「不一样」正常吗？ | **正常**。里面是你的任务、聊天、账号、心情——**每人一份私有数据**。 |
| 那大家怎么保证「表长得一样」？ | 靠 **Git 里的 C# 实体 + DbContext**，不是拷同一个 `.db` 文件。 |
| 要不要 TypeORM 那种 migration？ | **生产/多人长期协作** 建议有；**本课程演示项目** 当前用 `EnsureCreated` + 启动校验，是刻意简化的折中。 |
| 进 Git 的应该是什么？ | **实体类、`SpiritDeskDbContext`、（若采用）EF Migrations 文件夹**；不进 Git 的是 **`data/spiritdesk.db`**。 |

**一句话**：Git 管的是 **「库应该长什么样」的蓝图**；`spiritdesk.db` 是 **「你这台机器上已经存了什么」的实例**，两者分工不同，不能混为一谈。

---

## 1. 两个概念：Schema（结构） vs Data（数据）

```
┌─────────────────────────────────────────────────────────────┐
│  Schema（表结构）— 应该在团队间一致，由代码/迁移描述          │
│    UserProfiles 有哪些列？Tasks 有没有 DueAt？                │
│    → 来源：Core/Entities + Web/Data/SpiritDeskDbContext       │
└─────────────────────────────────────────────────────────────┘
                              ↓  EF 建表 / 迁移执行后
┌─────────────────────────────────────────────────────────────┐
│  Data（行数据）— 每人、每台机器可以不同                       │
│    你的昵称、任务标题、聊天记录、注册的 test 账号              │
│    → 存在：data/spiritdesk.db（运行目录下）                   │
└─────────────────────────────────────────────────────────────┘
```

类比：

- **Schema** ≈ Excel 的 **表头 + 列类型**（全组用同一份模板定义）。
- **Data** ≈ Excel 里 **你填的那几百行**（每人一份，不必提交到 Git）。

所以：**「每个人仓库里的 `.db` 不一样」** 若指的是 **里面的行不同**，完全正确；若指的是 **表结构对不上导致程序崩**，那才是要修的问题——修的是 **Schema 同步机制**，不是把每个人的 `.db` 提交进 Git。

---

## 2. 本项目里，什么在 Git、什么不在

| 内容 | 是否在 Git | 路径示例 |
|------|------------|----------|
| 表对应的 C# 类 | ✅ 是 | `SpiritDesk.Core/Entities/*.cs` |
| 列类型、索引、五精灵种子 | ✅ 是 | `SpiritDesk.Web/Data/SpiritDeskDbContext.cs` |
| 启动前表结构校验 | ✅ 是 | `SpiritDesk.Web/Helpers/DatabaseBootstrapper.cs` |
| 运行时补列（手写 SQL） | ✅ 是 | `SpiritDeskService` 里 `EnsureUserProfileSchemaAsync` 等 |
| EF Migrations（`dotnet ef migrations add`） | ❌ **目前没有** | 仓库内无 `Migrations/` 文件夹 |
| SQLite 数据库文件 | ❌ 否 | `{运行目录}/data/spiritdesk.db` |
| 删库前的备份 | ❌ 否 | `data/spiritdesk.backup-*.db` |

`.gitignore` 没有单独写 `spiritdesk.db`，是因为 **`data/` 目录本身就不会被提交**——它只在 `dotnet run` 后出现在 `bin/.../data/` 或 Shell 输出目录下，属于 **构建/运行产物**，和 `bin/`、`obj/` 一样不必入库。

## 3. 数据库文件从哪来？第一次运行发生了什么

启动链（简化）：

```
SpiritDeskWebHost.Build
  → 确定 dataDirectory（默认：AppContext.BaseDirectory/data）
  → databasePath = data/spiritdesk.db
  → DatabaseBootstrapper.EnsureCompatibleDatabase()   // 已有旧库则校验列
  → AddDbContext(... UseSqlite(...))

某次请求 / 初始化时 SpiritDeskService.EnsureInitializedAsync
  → dbContext.Database.EnsureCreatedAsync()         // 无库则按实体建表 + HasData 种子
  → EnsureUserProfileSchemaAsync()                  // 缺列则 ALTER TABLE（补列）
  → EnsureChatMessageSchemaAsync()
  → EnsureSpiritDefinitionsAsync()                // 五精灵配置与代码同步
  → 若无用户/任务/聊天则插入演示数据
```

### 3.1 `EnsureCreated` 是什么

`Database.EnsureCreatedAsync()` 的含义：

- 若 **数据库文件不存在**：按当前 `DbContext` 模型 **创建所有表**，并应用 `OnModelCreating`（含 `HasData` 五精灵种子）。
- 若 **数据库已存在**：**不会**根据你新改的实体去改表（不加列、不删列、不改类型）。

因此：**改实体后，老用户的 `.db` 不会自动变新结构**——这就是很多人以为「必须上 migration」的原因。

### 3.2 本项目怎么弥补「没有 Migration」

当前是 **三层补丁**（都在代码里，会进 Git）：

| 机制 | 做什么 | 数据会丢吗 |
|------|--------|------------|
| `DatabaseBootstrapper` | 用 `PRAGMA table_info` 检查必需列；对不上则 **备份旧库并删除**，下次 `EnsureCreated` 重建 | ⚠️ 会丢（有 backup 文件） |
| `EnsureWebAccountsTable` | 对老库 **幂等** `CREATE TABLE IF NOT EXISTS WebAccounts` | 否 |
| `EnsureUserProfileSchemaAsync` / `EnsureChatMessageSchemaAsync` | 缺某一列时 `ALTER TABLE ... ADD COLUMN` | 否 |
| `EnsureSpiritDefinitionsAsync` | 按代码更新五精灵文案/数值，没有则插入 | 否 |

这是 **演示向** 策略：小团队、表少、改结构不频繁时够用；**不是** TypeORM / 正规 EF Migrations 的替代品。

## 4. 和 TypeORM 对照：Migration 到底解决什么问题

### 4.1 TypeORM 常见流程

```
1. 改 Entity（加字段）
2. npm run typeorm migration:generate  → 生成 1735123456789-AddMood.ts
3. migration 文件提交 Git
4. 每个人 pull 后 migration:run  → 本地库执行 ALTER，保留原有行数据
```

特点：

- **带时间戳的 migration 文件在 Git 里**——全组执行同一份 SQL/变更脚本。
- **每个人的 `.db` 仍在本机**，但 **Schema 版本** 通过 migration 历史表（如 `migrations`）对齐。

### 4.2 EF Core Migrations（等价物）

```
1. 改 Entity / DbContext
2. dotnet ef migrations add AddLastSpiritSwitchAt
3. 生成 Migrations/20250521120000_AddLastSpiritSwitchAt.cs → 提交 Git
4. 每个人 dotnet ef database update  或  启动时 db.Database.Migrate()
```

| 对比项 | TypeORM | EF Core Migrations | 本项目当前 |
|--------|---------|-------------------|------------|
| Schema 定义在 Git | ✅ Entity + migration 文件 | ✅ Entity + Migrations/*.cs | ✅ Entity + DbContext |
| 升级已有库结构 | ✅ `migration:run` | ✅ `Database.Migrate()` | ⚠️ Bootstrapper 重置 或 手写 `ALTER` |
| 历史变更可追溯 | ✅ 时间戳 migration | ✅ 时间戳 Migration 类 | ❌ 散落在 Bootstrapper/Service |
| 适合生产多版本共存 | ✅ | ✅ | ❌ 演示向 |

**答辩说法**：我们了解 TypeORM/EF 的 migration 机制；课程演示阶段用 `EnsureCreated` 降低环境配置成本，表结构变更主要靠 **实体代码 + 启动校验**；若产品化会改为 **EF Migrations 并纳入 CI**。

## 5. 「每个人的库不一样」— 哪些该一样、哪些不必一样

### 5.1 应该一样（靠 Git + 同一套代码）

- 表名、列名、索引是否与 `SpiritDeskDbContext` 一致。
- 五精灵 **配置行** 是否与 `HasData` / `EnsureSpiritDefinitionsAsync` 一致（文案、路径可随代码更新）。

### 5.2 不必一样（本机 Data）

- 你是否注册过 `user1`、任务有几条、聊天记录、金币多少。
- 数据库文件路径（Shell 在 `bin/Debug/.../data/`，单独 `dotnet run` Web 也在各自 `bin` 下）——**路径可以不同，Schema 仍由同一份代码生成**。

### 5.3 错误理解 vs 正确理解

| 错误理解 | 正确理解 |
|----------|----------|
| 要把 `spiritdesk.db` 提交 Git，大家才能一样 | 提交的是 **建表规则**，不是 **你的存档** |
| 没有 migration 所以每人表结构一定乱 | 拉同一分支、删旧库或跑补丁后，**结构可以对齐**；乱的是 **没 pull 新代码仍用旧库** |
| 和 TypeORM 一样每人本地 `generate` 一份 migration | Migration 应 **团队共享一份在 Git**，不是每人各生成一套 |

## 6. 什么时候该上 EF Migrations（而不是继续 EnsureCreated）

建议在以下情况引入 `dotnet ef migrations`：

- 多人并行改表，需要 **可审查、可回滚** 的变更历史；
- 不能接受 `DatabaseBootstrapper` **整库重置** 带来的数据丢失；
- 需要 **保留用户数据** 仅做 `ADD COLUMN` / 改索引；
- 部署到服务器/Docker，要 **自动化** `Migrate()` 而不是手工删 `data/`。

引入后典型调整：

1. 删除或弱化「不兼容就删库」的 Bootstrapper 逻辑（或仅作最后一道防线）。
2. 启动改为 `await dbContext.Database.MigrateAsync()`，不再依赖 `EnsureCreatedAsync()`（二者不要长期混用）。
3. 把 `Migrations/` 目录 **纳入 Git**；仍 **不** 提交 `spiritdesk.db`。

## 7. 本机常见问题与处理

| 现象 | 原因 | 处理 |
|------|------|------|
| 拉代码后启动报错 / 缺列 | 旧 `spiritdesk.db` 与新区不匹配 | 看控制台是否 `[SpiritDesk] Reset local database`；或手动删 `data/spiritdesk.db` 再运行 |
| 五精灵文案改了但库里还是旧的 | `EnsureCreated` 不更新 HasData | 依赖 `EnsureSpiritDefinitionsAsync`；仍不对可删库重建 |
| Shell 和单独 Web 两套数据 | 两个进程 **运行目录不同**，各有一份 `data/` | 正常；演示时固定从 Shell 启动即可 |
| 想和队友「数据也一样」 | 那是 **Data** 同步需求 | 导出 SQL/拷贝 `.db` 文件私下传，**不要**进 Git；或用种子脚本 |

## 8. 若老师追问：你们有没有做数据库迁移？

**推荐答法（诚实 + 有深度）**：

> 我们用的是 EF Core + SQLite。表结构由 `SpiritDesk.Core` 的实体和 `SpiritDeskDbContext` 定义，跟代码一起版本管理。  
> 运行时数据库文件 `spiritdesk.db` 在本地 `data/` 目录，不进 Git，里面是每个用户自己的任务和聊天记录。  
> 项目目前没有使用 EF 官方的 Migrations 文件夹，而是用 `EnsureCreated` 建库，加上 `DatabaseBootstrapper` 校验列、以及 Service 里少量 `ALTER TABLE` 做增量补列；不兼容时会备份后重建。  
> 这和 TypeORM 里把 migration 文件提交仓库、每人 `migration:run` 的思路类似，只是我们演示阶段用更轻量的方式；若产品化会改成标准的 `dotnet ef migrations` + `Migrate()`。
